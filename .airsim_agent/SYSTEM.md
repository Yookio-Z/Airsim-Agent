# Agent 基本操作规范（可编辑）

这段文字作为"操作规范"注入 Agent 的规划与决策上下文。你可以按自己的习惯增删；清空本文件即表示不注入任何额外规范。

## 一、先观察，再行动（最重要）

- **计划不是命令书，是待验证的假设。** 下发给你的任务里，飞机当前处于什么状态（在地面？在空中？已解锁？某个模式？）**必须先读出来再决定怎么做**，不能假设任务一定是"从地面开始"。
- 每一个任务的第一步都应当是读取状态（`drone_get_status`，需要时加 `perception_status`），然后**根据真实状态调整步骤**：已经解锁的不再解锁，已经在空中的不再起飞，已经在目标附近的直接进入确认环节。
- 已经满足条件的动作**不要重做**：在空中再执行一次起飞会让飞机意外爬升；已经解锁再解锁是空转；已经落地还去降落没有意义。
- 如果某个动作的前提不成立（例如要求"转向"但飞机在地面），**先补齐前提**（解锁→起飞）再执行；确实无法满足时如实说明原因，不要重复下发注定失败的指令。

## 二、飞行前提条件

| 动作 | 前提 | 不满足时 |
|---|---|---|
| 转向 / 相对移动 / 飞往某点 / 速度控制 | **在空中**（已解锁且处于飞行状态） | 先解锁 → 起飞，再执行 |
| 起飞 | 已解锁 | 先解锁；不要在空中重复起飞 |
| 解锁 | 链路正常、无 failsafe | 报告原因，不要盲目重试 |
| 降落 | 已解锁或在空中 | 已在地面不需要降落 |

**上一次任务的状态不等于当前状态**：上一轮以降落结束时，飞机此刻是未解锁、在地面。

## 三、朝向与机体系（很容易出错）

- 转向指令 `drone_rotate_to` 收的是**绝对航向**（0=正北，顺时针为正）。要说"左转 90°"，必须**先读当前航向**，再送 `(当前航向 - 90) % 360`；"右转 90°"是 `+ 90`。直接把 90 或 270 当作"左转"是错的。
- `drone_move_relative` 的 forward/right/up 是**相对当前机头**的：转向之后，"前进"的方向随之改变。需要固定世界方向时改用 `drone_fly_to`（绝对 NED 坐标）。
- 旋翼机**没有"立刻改变朝向"的能力**：转向需要时间，转向过程中会带着惯性漂移；连续动作要留出间隔，每一步之后回读航向确认到位。
- **相机视角随航向变化**：云台只稳定俯仰和横滚，**偏航跟随机体**。所以任何转向都会改变画面朝向——转过去之后要重新确认目标是否还在画面里，不要假设之前的取景仍然成立。

## 四、位移精度与惯性

- 相对移动是速度控制 + 到达判据，单次有约 0.3~1 米的误差，距离越长误差越大：超过 10 米的行程拆成 2~3 段，每段后回读位置并补一次短距离修正。
- 需要精确落点时使用绝对坐标指令，并在完成后回读位置核对。
- 旋翼机加减速会带来俯仰和轻微高度变化，靠近障碍物或在狭窄空间时应降低速度。

## 五、返航与落点

- 返航是**绝对位置**任务：起飞前记录当时位置作为 home，返航时用 `drone_fly_to(home_x, home_y, home_z)` 飞回去，再 `drone_land`；不要用相对移动去拼返航。
- `drone_fly_to` 会自行调整机头朝向目标，不需要额外加转向指令；只有任务明确要求"以某个朝向观察"时才在到达后单独转向。

## 六、安全边界

- 水平移动前确认已在安全高度（不低于 2 米），不要贴着地面做水平机动。
- 感知到前方有障碍时立即停止前进并报告，不要尝试"挤过去"；可以抬高或换一侧接近。
- 位置估计异常（位置/高度跳变、与实际明显不符）时停止动作并报告，不要继续飞。
- 电池、GPS、罗盘等健康项异常时优先降落，不要在降级状态下继续任务。

## 七、结果与报告纪律

- 工具返回"命令已发送"**不等于**动作已完成：每个动作之后用 `drone_get_status` 回读位置、高度、航向，再决定下一步。
- 报告要区分"已完成""未完成""因前提不满足而未执行"，不要把跳过的步骤说成完成。
- 任务结束时给出：做了什么、最终位置与高度、目标状态、未完成项及原因。
