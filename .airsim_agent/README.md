# Agent 的家（`.airsim_agent/`）

这个目录装 Agent 的一切，结构对照 pi 项目的 `.pi/`：**手册入库，数据不入库**。

```
.airsim_agent/
  SYSTEM.md                      # 常驻系统提示词（入库；UI 设置面板可编辑）→ 原 config/agent_system.md
  NOTES.md                       # 长期笔记（入库；每轮随 SYSTEM.md 注入，操作员维护）
  README.md                      # 本文件（入库）
  skills/<skill-name>/SKILL.md   # 技能（入库）
  memory.json                    # 长期记忆：facts / lessons / 工具统计（不入库，运行时生成）
  sessions/                      # 界面会话历史（不入库，运行时生成）
  session_memory/                # 每个会话的记忆快照（不入库）
  task_runs/                     # 任务运行记录（不入库，最多保留 80 条）
  runs/                          # run 级审计 jsonl（不入库，最多保留 200 个）
  attachments/                   # 会话附件图片（不入库）
  settings.json / models.json    # 本机设置与模型配置（不入库）
  secrets.json                   # LLM 密钥（不入库，绝不提交）
```

技能是**操作知识**，不是动作。它们教 Agent 如何执行一类任务、该伸手拿哪些原生工具；
每一个飞行动作仍然走普通工具面、过普通安全闸门。

## 记忆：文件和日志，不是工具（2026-10-15 定稿，参照 pi）

产品**没有记忆工具**（原先的 memory_store / memory_recall / memory_remember 已删除）。
按 pi 的做法分两层：

| 层 | 载体 | 谁写 | 怎么进模型 |
|---|---|---|---|
| 知识 | `SYSTEM.md` + `NOTES.md` | 操作员 | 每轮自动注入上下文（各 4000 / 2000 字上限） |
| 历史 | `memory.json`、`runs/`、`session_memory/` | 运行时自动写 | 只注入有界摘要（工具成功率、经验教训、上次做到哪） |

要看历史全文：界面「记忆」与「任务运行」面板。要让 Agent "记住"什么：写进 `NOTES.md`。

**数据分两处，按"属于谁"划分**（2026-10-19 定稿）：

- **Agent 自身** → `.airsim_agent/`：手册、会话、记忆、审计、附件；
- **飞行数据资产** → 顶层 `data/flightlog/`：飞机遥测记录，只增不改，供分析/导出。
  刻意不放进 `.airsim_agent/`——"清空 Agent 家 = 失忆"的操作不能连带删掉飞行数据。

`src/` 里不存放任何运行期数据（原 `src/data/` 已迁移并删除）。

## 技能目录约定

`<skill-name>` 与 frontmatter 里的 `name:` 必须完全一致，且只能是小写字母、数字和连字符
（最长 64 字符，不能以连字符开头/结尾，也不能有连续连字符）。

## 技能如何到达模型

分两层，未使用的技能几乎不占成本：

1. **目录（常驻提示词）。** 对每个启用的技能，模型只看到 `name`、`display_name` 和
   `description`——约 50–100 tokens。description 就是触发信号：它必须说明**这项技能覆盖
   什么、什么时候用**，用祈使语气（"当……时使用本技能"）。
2. **正文（激活时加载）。** 当某条描述与任务匹配时，模型发出该技能的动作名
   （`skill:<name>`）作为动作。运行时随后把完整的 `SKILL.md` 正文作为观察返回，模型照着
   它去选择原生工具。

没有 description 的技能永远无法被触发，所以 description 不是可有可无的装饰。

## Frontmatter

| 键 | 作用 |
|---|---|
| `name` | 必需。技能身份（`skill:<name>`）；必须等于目录名。 |
| `description` | 必需。触发信号——说明它覆盖什么**以及**什么时候用，并写进操作员真会说的原话。 |
| `status` | `disabled` 或 `archived` 会完全隐藏该技能。UI 在开关技能时写入此字段。 |
| `required_capabilities` | 当前后端不提供全部所需能力时，该技能被隐藏。 |
| `display_name`、`cost`、`risk`、`type`、`subtools` | 仅用于展示与目录的元数据。 |
| `when_to_use` | 仅作后备：优先把"何时使用"写进 `description`。 |

## 如何写好一份 SKILL.md

- **正文控制在约 500 行以内。** 长参考资料移到 `references/` 并在正文里指过去。
- **每条规则都锚定到真实工具。** 用"意图 → 工具"表格给出确切的工具名和关键参数，
  优于用散文描述意图。
- **承重的指令放在靠前位置**——正文可能被截断。
- **解释规则为什么重要**，而不是堆大写 MUST；模型对有理有据的约束遵守得更可靠。
- **写明这项技能不适用于什么。** 边界声明能阻止错误的技能被激活——但注意模型是用
  description 而不是正文来决定激活的。
- **不要发明工具或字段。** 如果技能写了一个未注册的工具，或一个在该后端上恒为 null 的
  快照字段，Agent 会在它上面白白烧掉轮次。先核对工具面。
- **节标题用规范中文名。** `## 目的`、`## 使用时机`、`## 失败处理`、`## 验证`、`## 输入`
  这几个标题会被解析器读进工具卡片字段（描述、when_to_use、失败策略、验证、输入参数），
  必须逐字使用（解析器同时兼容旧的英文标题）；其余标题（工作流程、核心规则、不适用等）
  自由书写。

## 现有技能

| 技能 | 覆盖内容 |
|---|---|
| `flight-sequence` | 一条紧凑指令串起多个单机步骤：状态 → 解锁 → 起飞 → 移动 → 拍照 → 视觉分析 → 返航 → 降落。 |
| `visual-approach` | **接近路径。** 飞向任何看得见的目标：视觉模型点位 + 深度距离循环、90° 像素-米换算、穿过开口、降落在小物体上。 |
| `target-inspection` | 近距查证与重获：移动前"看一眼 + 读一次深度"、用粗估归一化高度表达的占画面比例停止规则、挪位前先确认朝向、障碍拦停接近。 |
| `region-search` | 从空中寻找 / 确认 / 跟踪目标，带严格的视觉模型观察预算（每朝向一次、≤8 朝向 × ≤3 位置）和诚实的"没找到"。 |
| `formation` | 通过 `formation_command` 做多机编队飞行与区域覆盖。 |

## 感知决策（项目级）

目标检测器已**从本项目移除**：工具面里没有任何检测器工具。感知路径是
**"视觉模型管语义 + 深度管米制距离"**——`inspect_current_frame` 回答"在不在 / 是什么 /
大致在哪多大"（它的 `bbox_hint` 明确是粗估）。所有几何量都走**一个**工具：
`locate_image_point(points="x,y;x,y;x,y")` —— 归一化点（可多点，取中值/最小值）
加无人机位姿，一次换算出 `distance_m`（米数、`distance_median_m`）和 NED
`world_pos`。`perception_status` 现在只报告**相机健康**（online、fps、`capture_age_s`、
view）——它不携带目标。接近类任务由 `visual-approach` 负责。

## 历史：可执行技能已删除

早期设计里技能是可调用的 Python 执行器（`navigation`、`search`、`visual_observe`、
`return_home`）。它们从未被生产运行时注册（生产环境选注册表开关一直是关的），
2026-10-14 清洗时连同该开关一起删除——技能面现在**只有** SKILL.md 文档，飞行动作
全部走原子工具。

`SkillRegistry.register()` 保留为空扩展点（当前无任何调用方）：将来若引入确定性算子，
再从那里注册执行器。

**注意：当前只加载 `SKILL.md` 本身。** `references/` 与辅助脚本子目录**没有加载器**，
不要在技能目录里放依赖代码——需要代码的能力属于工具/算子层（运行时代码），技能文档
只描述怎么用它。
