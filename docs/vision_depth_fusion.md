# 视觉 × 深度：把两种模态合起来用（2026-10-13）

> 起因：实跑里飞机"直飞一个用单点深度推出来的坐标"，掠过汽车、目标出画，之后再也
> 找不到它。操作员的两个判断都对：**定位不对**、**我们没有真正把 VLM 的画面信息和
> 深度信息结合起来**。这份文档记录诊断、已落地的融合检查、以及为什么"加激光雷达"
> 不是这个问题的解。

## 1. 诊断：深度没错，点错了

那次失败的关键数字（来自运行记录）：

```
airsim_locate_point(0.6, 0.39) → valid=True, distance_m=30.0, angle_v_deg=-9.0
```

- 30 m 是**那条视线方向上**的表面距离，视线向下 9° → 打中的是相机下方数米的**路面**，
  不是画面里那辆远处的车。
- 深度图的读数本身是可信的（AirSim 的 `DepthPlanar` 是逐像素真值）——**错的是"这个
  像素不是目标"**。同一个像素换激光雷达去测，还是 30 m。

结论：这不是测距精度问题，是**关联/校验问题**。以前没有任何机制能发现它，因为
"VLM 给一个点"和"深度给一个数"之间没有任何交叉验证——正是指出的"模型理解片面化"。

## 2. 已落地的融合（都在代码里，不靠提示词自觉）

| 机制 | 位置 | 作用 |
|---|---|---|
| **框内外深度对比** `surface_check` | `perception_airsim_adapter._surface_consistency` | 传了视觉框（`w`,`h`）后，工具在**框内 4 点**与**框外 4 点**各取深度中值：`same_surface`（内外一致 → 画的是一整片连续表面，不是目标）/ `object_in_front`（内更近 → 像独立前景目标）/ `recessed_or_far`（内更远 → 洞/门后/远处） |
| **米制尺寸换算** `metric_size` | 同上 | 由 `深度 × 归一化尺寸 × 2` 给出目标实际宽高（车≈1.8 m），供模型做量级把关 |
| **探测点警告** `probe_warning` | `project_point_to_world` | 视线下倾 ≤ −8° 时明说"这个点很可能在目标前面的地面/路面上，不要据此飞过去" |
| **运行时否决"飞过目标"** | `agent_loop._approach_overshoot_reason` | 近距接近任务里，`drone_fly_to` 落点进入"已定位目标点"的站离圈或更远 → 否决并交回模型（`surface_check=same_surface` 的坐标不被当作目标，避免误拦） |
| **"单次定位不可信"纪律** | `skills/visual-approach` | 走一段 → 重新看图 + 重新测距 → 更新估计；2–3 轮迭代收敛，而不是一次直飞 |

工具签名相应变为 `airsim_locate_point(x, y, w, h)`；卡片、系统提示、技能都写明
"**强烈建议传 w/h**"，因为不传就没有内外对比可言。

## 3. 为什么"加激光雷达"不是这个问题的解

- AirSim 的深度图是**仿真真值**（逐像素解析距离），激光雷达测的是同一个几何：那个
  像素依然是 30 m。"点错了"不会因为换传感器而变对。
- 激光雷达真正能补的是**另一件事**：净空/障碍真值（比我们现在用深度点采样估计前方
  净空靠谱）。如果要做，它是一个独立小项目：settings 加 `LidarSensor` → 加一个只读
  工具 → 前向净空判定；但它不回答"画面里哪一坨才是车"。
- 仿真里真正"知道物体在哪"的替代品是 AirSim 自带的物体级真值
  （`simGetDetections` / 分割图）——仿真专属、不可迁移到真机，与"可迁移的 VLM+深度"
  路线冲突，建议只用来做评测对照，不进入运行时。

## 4. 仍然存在的边界（如实记录）

- 框内外对比用的是**视觉模型的粗框**（±30%），阈值取得宽（±20%）；目标贴墙、半遮挡、
  或在纯背景纹理上时，判别会退化到 `unknown`。此时行为是"不给结论"，而不是猜。
- 融合结论目前作为**工具返回值**交给模型判断。如果要把"已知是地面还硬要飞过去"变成
  运行时的硬否决，扩展点已经在 `_approach_overshoot_reason`（同一条否决路径），
  一行判断即可加上——需要操作员确认后再开。
- 迭代收敛（走一半再重估）依赖模型遵守技能纪律；运行时能保证的是"每次观察后必须
  由模型重新决定参数"（`needs_observation` 交接）与"飞过目标会被否决"。

## 5. 停止判据：由任务声明，运行时只评估（2026-10-13 第三版）

**原则：判定标准属于任务，不属于运行时。** 两版演进的教训：

- 第一版：运行时写死常数（"目标占画面 ≥25% 才算到位"）→ 把靠近类任务的标准强加给
  所有任务（落点类任务要的是位置精度，不是"靠得够近"）。
- 第二版：写死 + "没声明时按任务类型兜底" → 仍然是运行时在替任务发明标准。
- **现在**：只在任务**声明**了判据时才评估、播报、执行；**没有声明就不判**——
  运行时不发明标准、不替模型拿主意，完成由模型自己判断（`is_complete`）。

判据来自 `goal.success_criteria`（规划器按指令写，白名单内、参数被清洗）：

| 判据 | 含义 | 数据来源 |
|---|---|---|
| `target_fill{min_fill}` | 目标占画面高度达到阈值 | 视觉模型的 `bbox_hint.h`（粗值 ±30%） |
| `target_distance{max_m}` | 目标距离小于等于阈值 | 深度 / 点位投影 |
| `position_reached{x,y,z,tolerance}` | 位置到达坐标（水平与高度都在容差内） | 自身遥测 vs 目标坐标 |
| `flying_at{altitude,tolerance}` | 定高保持 | 高度遥测 |
| `landed` | 已落地 | 遥测 `flying=false` |
| `target_confirmed` / `photo_taken` / `status_ok` / `mission_progress_complete` / `formation_stable` | 语义类 | 工具结果 |

声明了判据之后，运行时做三件事：
1. **评估并播报**：判据满足时在时间线上留一行"已到达任务判据（fill=0.41 min_fill=0.25）"；
2. **拒绝与该判据背道而驰的动作**：判据已满足还继续"大幅逼近"（`move_relative forward_m > 1 m`
   或"向目标靠近的 `fly_to`"）→ 否决并交回模型（允许 ≤1 m 的微调，供"贴近看清细节"）；
3. **有界收尾**：连续两次否决后仍在逼近 → 运行时按"判据已满足"收尾（`is_complete`）。

**位置类判据出现时，运行时不作"占画面比例"的判定**——那类任务由位置判据自己管
（`_verify_completion` 在收尾时评估，不满足则如实标 blocked/未达成）。

## 7. 判据按"任务要什么"分类（通用，不针对某个具体场景）

| 任务要什么 | 该声明的判据 | 精度取决于 |
|---|---|---|
| 接近程度（靠近观察 / 靠近悬停） | `target_fill` 或 `target_distance` | 视觉尺寸（粗）与深度 |
| **位置精度**（落点、定点、穿越后停住） | `position_reached` ± `landed`/`flying_at` | **目标坐标的估计质量**——所以这类任务必须迭代定位（靠近→重新看图+重新定位→收敛），容差要按估计误差给 |
| 语义结果（找到了/确认了/拍到了） | `target_confirmed` / `photo_taken` | 视觉模型的判断 |

两个通用限制（不是某个场景的特例）：

1. **位置精度受限于"目标在哪"的估计**：我们只有视觉点 + 深度 + 位姿的投影，单次探测的
   误差会直接变成位置误差；要更准只能迭代，或者未来引入不依赖视觉的定位源。
2. **"与周围同属一个连续表面"的目标（平放在地面上的标记、贴墙的图案）无法用
   深度差异验证**：那类目标要用**外观/尺寸**信号（VLM 回答"标记是否居中、占画面多大"）。

## 8. 下一步

1. **判据可视化**：把"当前任务的判据 + 实时状态"放进操作员界面（例如
   `target_fill ≥ 0.25 —— 当前 0.18`），让"怎么算做到"对操作员可见，而不是只在收尾报告里。
2. **语义型判据（VLM 判定）**：允许任务声明"用一句话描述的完成条件 + 评分要点"，由 VLM
   按要点回答是否满足（带证据引用与滞后确认）。这能覆盖"外观/关系"类条件而无需为每类任务写代码——
   设计细节待 VLA/机器人成功检测的调研结论（进行中）。
3. **缺的判据类型**：穿越类（以某个平面为界的"已穿过"）。
