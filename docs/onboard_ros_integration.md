## 0. 一句话结论

"对接机载 ROS"不是一个传输问题，是四个独立问题：**传输、视频配准、目标身份、控制权**。
其中**控制权是唯一会摔飞机的那个**，而它有一个不需要发明新协议的解：

> **机载跟踪算法不直接发 `/fmu/in/*`，把控制意图交给 gateway；gateway 保持 `/fmu/in/*` 的唯一发布者。**

这正是 `ros_provider_bridge.md` 已经写下的原则（"The gateway remains the deterministic PX4 control boundary"）。
两个进程同时给 `/fmu/in/trajectory_setpoint` 发流，PX4 取最后到达的那条，等于每 tick 抛硬币。把发布权收在 gateway 一处，"谁在控制"就退化成一个进程内的互斥量，而不是一个分布式一致性问题。

## 0.1 两个时间尺度：这是慢环，不是控制反馈

"地面要指挥、又要看画面，两条链路协调不了"这个直觉成立的前提是：**地面在下行画面里看到目标 → 决定 → 下发**要形成一个闭环，并且机载的跟踪精度依赖这个闭环。
这个前提不成立。系统里有两个时间尺度完全不同的环：

| 环 | 内容 | 延迟要求 | 谁闭合 | 链路参与吗 |
|---|---|---|---|---|
| **快环** | 检测 → 目标状态 → 控制律 → setpoint | **必须 <100ms** | 机载，自主 | **完全不参与** |
| **慢环** | 看画面 → 判断 → 改选目标 / 中止 / 改约束 | **1~3s 足够** | 人 + 地面 Agent | 参与，但要求宽松 |

**跟踪精度由机载快环保证，与链路无关。** 地面看到的画面延迟 300ms 还是 2s，都不影响飞机跟得住目标——它只影响操作员的"感知新鲜度"。

慢环的预算（量级）：

| 环节 | 延迟 |
|---|---|
| 相机 → 编码（nvenc） | 20~50ms |
| 视频 → 地面 → 解码显示 | 150~400ms（WiFi，buffer=1）；图传 0.5~2s |
| 人看一眼并决定 | **1~2s** |
| 指令 → 机载执行 | 10~50ms（WiFi）；数传 <1s |
| **慢环合计** | **≈1.5~3s，其中人是主要项** |

结论：**慢环的瓶颈是人，不是链路。** 两条链路之所以"难协调"，是因为默认了它们要在控制回路上对齐；一旦把它们放进不同的环，需要协调的地方就只剩下三个离散握手点（§8 选定目标、§6 控制权转移、中止），每个都有明确回执，都不是高频流。

唯一硬要求：**中止不能被链路吞掉**，见 §3.4 的优先级与限流设计。

## 1. 问题分解

| 编号 | 问题 | 本质 | 不解决的后果 |
|---|---|---|---|
| P1 | **传输** | 命令/状态/检测怎么过链路 | 现在只有 HTTP + 1Hz 轮询，选目标 UX 不可用 |
| P2 | **视频配准** | 画面怎么到地面，框怎么画在画面上 | 操作员看到的框和真实画面错位，点选点到错误目标 |
| P3 | **目标身份** | 用户说"那辆白车" → 落到哪个 track_id | 锁定漂移，跟错目标 |
| P4 | **控制权** | 同一时刻谁有 setpoint 发布权 | 地面和机载互相抢控制，飞机抖振或失控 |
| P5 | **断链** | 链路断了机载怎么办 | 飞机带着一个已失去监督的闭环继续飞 |

这四个问题**必须分开设计**，任何一个用"再加一个 HTTP 接口"的方案都会在另外三个上翻车。

## 2. 三个平面

```text
┌──────────────────────────── 地面站 (Windows) ────────────────────────────┐
│  Agent / 对话 / 技能              视频面板 + 候选缩略图 + 控制权指示 + 中止 │
│        │                                        ▲                        │
│        │ 指挥面 (小消息, 可靠, 10~30Hz 推送)      │ 视频面 (高码率, 独立)   │
└────────┼────────────────────────────────────────┼────────────────────────┘
         │  WebSocket / JSON+MsgPack              │  RTSP / WebRTC / MJPEG
         │  (可换 Zenoh/DDS, 见 §3)                │  (与指挥面解耦)
┌────────▼────────────────────────────────────────┴────────────────────────┐
│                        机载电脑 (Jetson / Orin)                           │
│  edge_agent ── 算法 supervisor ── 跟踪算法进程                            │
│       │              │                  │                                │
│       │              │                  │ 控制意图 (ROS topic)            │
│       │              │                  ▼                                │
│       │              │            ┌───────────┐                          │
│       │              └───────────►│  gateway  │◄── 安全面: 权威租约+看门狗 │
│       │                           │ (唯一发布) │                          │
│       └──────────────────────────►└─────┬─────┘                          │
└─────────────────────────────────────────┼─────────────────────────────────┘
                                          ▼  /fmu/in/*  (offboard)
                                        PX4
```

**三条原则**：
1. 指挥面和视频面**永远分离**。不要把视频塞进命令通道，也不要把命令塞进图传。
2. 机载算法**不直接碰飞控**，只发"控制意图"，由 gateway 翻译并发布。
3. 地面站的 Agent 只看到**语义能力**（选目标、锁定、跟随、中止），看不到 ROS 图。

## 3. P1 传输选型

### 3.1 候选方案对比

| 方案 | 能力 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **HTTP + 轮询**（现状） | 请求/响应 | 已有、好调试 | 1Hz、无推送、检测延迟 → 选目标不可用 | 保留为兜底/健康检查 |
| **WebSocket + MsgPack** | 双向、推送 | 单端口、NAT/防火墙友好、push 10~30Hz、Python 两端都好写、`wscat` 可现场调试 | 需自己定协议（约 150 行） | **主选** |
| **gRPC 流式** | 双向流、强类型 | protobuf 契约明确、多语言 | 需 protoc 工具链、调试比 WS 麻烦 | 想要强类型契约时选它 |
| **Zenoh (`zenoh-bridge-ros2dds`)** | 原生 ROS topic/service | 机载跑官方 bridge，**地面用 zenoh-python 直接订阅 ROS 话题，Windows 上不用装 ROS**；订阅式带宽控制；TCP/TLS 穿 NAT | 多一层组件；Action 映射取决于 bridge 版本，需在目标版本上验证 | **想要原生 ROS 语义时的升级路径** |
| **ROS 2 DDS 直连** | 原生全能力 | 零适配，rviz/foxglove 直接可用 | Windows 装 ROS 2；DDS 组播发现过 WiFi 很脆；默认无鉴权；带宽控制粗 | 实验室可以，外场不建议 |
| **foxglove_bridge** | ROS 话题/服务 over WS | 现成可视化生态，Image+Detection 话题开箱即看 | 集成进自有 UI 要么实现其协议要么嵌 Foxglove Studio；不做控制面 | 调试用很好 |
| **MAVLink 隧道** | 极小命令 | 复用现有链路 | 变相滥用协议，带宽/语义都不合适 | 不建议 |
| **SSH + `ros2 launch`** | 起进程 | 零机载侧代码，今天就能用 | 无结构化状态、进程监管靠 ad-hoc、断链后进程残留 | **仅作手动引导兜底** |

### 3.2 为什么主选 WebSocket 而不是继续用 HTTP

现状 `RemotePerceptionEngine` 轮询 `/health`+`/snapshot`+`/events`，**默认 1.0 秒一次**（`src/modules/perception_axis.py:786`）。
做"看着实时画面点选目标"时，1Hz 意味着你点下去那一刻屏幕上显示的目标位置最多是 1 秒前的——目标动一下就选错。检测/状态推送必须到 **10~30Hz**。

WebSocket 场景下三条流复用一条连接：

```text
→ C→S  rpc        {id, method, params}                        # 请求/响应
→ C→S  subscribe  {topic: "targets" | "status" | "algo_status"}
← S→C  rpc_result {id, ok, result}
← S→C  event      {topic, seq, ts, payload}                   # 推送
← S→C  heartbeat  {ts, rtt_hint}
```

带宽是小事：10 个目标 × 30Hz × 约 120 字节 ≈ 36 KB/s，比视频低三个数量级。

### 3.3 地面站侧要做的抽象

在 GCS 里定义**一个**接口（例如 `EdgeUplink`：`rpc()` + `subscribe()` + `health()`），底下可插 HTTP / WS / Zenoh 实现。
Agent 工具、技能、审批门**只依赖这个接口**。这样"传输"这个决策永远不会泄漏到 Agent 层，将来从 WS 换 Zenoh 不动业务代码。

现有 `RosProviderBridgeClient`（`src/agent/ros_provider_bridge.py`）已经是这个形状的雏形，扩展它而不是另起一套。

### 3.4 链路预算与优先级

两个方向的带宽需求差三个数量级，这决定了它们必须走不同的物理链路：

| 流 | 速率 | 说明 |
|---|---|---|
| 心跳 + 状态 | 2Hz × ~1KB ≈ **2 KB/s** | 恒定，最小 |
| 检测/目标流（全候选 30Hz） | 30Hz × 10 目标 × 120B ≈ **36 KB/s** | WiFi 可承受 |
| 检测/目标流（降级：仅主目标） | 5Hz × 150B ≈ **750 B/s** | **数传（几 KB/s）可承受** |
| 视频 | 720p H.264 ≈ 1~2 Mbps ≈ **125~250 KB/s** | 必须独立链路 |

**速率自适应**：指挥面必须按实测带宽降级——WiFi 推全候选 30Hz，数传自动降到"主目标 5Hz + 事件驱动"。别把全量候选流当作恒定需求。

**优先级分离**（重要）：
- `abort` / `hold` / 控制权接管 属于**独立的高优先级控制帧**，不能和"查询日志 / 启动算法 / 拉全量候选"共用一个队列。
- 做法：控制帧走独立的 priority 标记，出站队列紧张时**丢大消息、保控制帧**；或控制帧走一条独立的轻量通道。
- 反面教材：一次 `GET /algorithms/{id}/status` 返回 50 行日志把出站缓冲占满，操作员的中止指令排在后面 200ms 才发出去。

**不对称降级**（只断一边时）：

| 情况 | 机载 | 地面 |
|---|---|---|
| 视频断，指挥面在 | 按当前模式继续（自主） | 看不到画面，但**仍能中止**（小包能过） |
| 指挥面断，视频在 | 继续自主；心跳超时后按 `link_loss_policy` | 只能看，必须告警"控制面已失联" |
| 都断 | 按 `link_loss_policy`（起飞前设定） | 重连后从事件流补状态，**先确认权威归属再下令** |

## 4. P2 视频与配准

### 4.1 视频面选型

| 方案 | 端到端延迟 | 720p 码率 | 适用 |
|---|---|---|---|
| 独立图传 + 地面接收盒 RTSP（现有路线） | 1~3s | 由图传决定 | 只看热闹够用；点选目标偏慢 |
| 机载 H.264 → RTSP（`nvenc`/`x264enc`） | 0.5~1.5s | 1~2 Mbps | **默认推荐**，机载编码不占多少 CPU |
| WebRTC | 0.15~0.4s | 1~3 Mbps | 需要低延迟手动监视/点选时升级 |
| MJPEG over HTTP | 0.15~0.4s | 480p@5fps ≈ 1~2 Mbps；720p@10fps ≈ 5~8 Mbps | 实现最简单；弱链路别用 |
| ROS `Image` 话题过桥 | — | 裸图 1080p@30 ≈ 186 MB/s | **禁止**；只允许 `CompressedImage` |

结论：**默认走机载 RTSP，需要 <400ms 时换 WebRTC**。不要把视频和指挥面绑在一起。

### 4.2 框怎么画在画面上（关键细节）

两条路，**都做**：

1. **时间戳配准（主路，用于点选）**
   - 检测消息带 `frame_ts`（机载时钟）与 `frame_seq`，bbox 用**归一化坐标** `[0,1]`。
   - 地面维护 1~2s 的视频环形缓冲，用 ping 估一个常值时钟偏移，按 `frame_ts` 找对应帧再画框。
   - 归一化坐标的意义：地面显示端无论缩放多少，**只要不做裁剪**（letterbox 不 crop），屏幕点击 → 归一化坐标是精确映射，点选才不会错位。
   - 残余误差主要来自视频路径延迟抖动，通常 ±1 帧，可接受。
2. **机载烧框流（辅路，用于信任）**
   - 机载直接推带框的视频。所见即算法所见，操作员最信任，配准零成本。
   - 代价：机载编码 CPU；且框"焊死"在画面上，不能做点选命中测试。

**同一台相机是前提**：机载检测用的相机必须和地面看的画面是同一路（或同一物理相机的两路分发）。如果检测用的是吊舱、地面看的是另一路，时间戳配准方法失效，只能走烧框流。

### 4.3 现有代码缺口

`PerceptionAxis.annotated_frame()`（`src/modules/perception_axis.py:1015`）用 `getattr` 探测引擎是否实现该方法，而 `RemotePerceptionEngine` **没有**实现 → **remote 模式下地面站完全没有画面**。
远程模式必须补 `annotated_frame`（拉一路 JPEG/接管 RTSP 流），否则外场操作员面前是黑的。

## 5. P3 目标身份与锁定交接

### 5.1 地面永远只下发"身份"，不下发控制律

```text
lock(track_id=17, mode="follow")            # 首选：机载跟踪器自带 ID
lock(point=[0.42, 0.55], frame_ts=..., mode="follow")   # 退化：无 ID 时用点选+帧号
```

**必须有稳定的 `track_id`**（ByteTrack / BoT-SORT 这类跟踪器天然提供）。
如果机载跟踪器不给 ID，就要退化成"在指定帧的指定框上初始化"，这要求跟踪器持有短时帧/特征缓冲——通常比自己加个 ID 更难，所以**优先推动机载侧输出 track_id**。

### 5.2 两步握手，绝不假设成功

```text
C→S  lock {track_id: 17, mode: "follow"}
S→C  {state: "locking", track_id: 17}
S→C  {state: "locked",  track_id: 17, class: "car", confidence: 0.91}   # 或
S→C  {state: "failed",  reason: "target_lost"}
```

地面 UI 只有在收到 `locked` 之后才显示"已锁定 #17"，并**才允许**进入跟随。
`locked` 里回带的 ID 与请求不一致时（跟踪器重新分配了 ID）必须按新的 ID 更新，不能沿用旧的。

### 5.3 跟随是"具名行为"，不是控制律

机载对外暴露的是语义档位，地面 Agent 选档位：

| mode | 语义 |
|---|---|
| `follow` | 保持设定距离跟随（水平距离 / 相对高度可配） |
| `orbit` | 绕目标盘旋（半径、角速度可配） |
| `keep_in_view` | 只转机头/云台保持目标在画面内，**不移动位置** |
| `hover_and_watch` | 悬停观察 |

**距离、高度、半径这些安全参数必须由地面显式给定或走已展示的默认值，绝不能由 LLM 自由生成。**

### 5.4 目标世界坐标由机载给

目标的地理/局部坐标由机载算（它知道自己位姿 + 相机内参）。地面**不要**从压缩视频里反算目标位置——精度和延迟都不可接受。
扩展现有 snapshot 结构而不是发明新结构（`perception_axis_design.md` §7 已冻结）：

```json
{"targets": [{
  "track_id": 17, "class": "car", "confidence": 0.91,
  "bbox": [842, 511, 961, 590], "norm_bbox": [0.439, 0.473, 0.501, 0.546],
  "center": [901, 550], "age_s": 12.4, "frame_ts": 1730000000.123,
  "world_pos": {"x": 12.3, "y": -4.1, "z": 0.4}, "distance_m": 18.6
}], "primary": null, "timestamp": 1730000000.2}
```

### 5.5 不可靠链路上的目标引用：帧引用法（关键机制）

这是回答"两条链路延迟不同、时钟不同步，地面点选会不会选错"的核心机制。

**反面做法（不能用）**：地面把屏幕坐标换算成方位角或世界坐标下发，机载按这个坐标去找目标。
坐标来自几百毫秒前的旧帧，目标已经移动；而且地面无法保证机载相机与显示端裁剪方式一致。

**正确做法**：地面下发的是**对机载某一帧的引用**，由机载自己解析成自己的 track_id。

```text
C→S  select {frame_id: 884213, norm_point: [0.42, 0.55]}
S→C  {state: "resolved",  track_id: 17, class: "car", confidence: 0.91, age_s: 12.4}
 或  {state: "failed",    reason: "reference_expired", buffer_depth_s: 5.0}
 或  {state: "ambiguous", candidates: [...], reason: "point_on_two_boxes"}
```

机载侧要实现三件事，都很小：

1. 每帧打一个单调递增的 **`frame_id`**（机载自己产生），随检测结果一起下发；
2. 保留 5~10 秒的 **`frame_id → detections(with track_id)` 环形缓冲**；
3. 收到 `select` 时按 `frame_id` 查缓冲，用 `norm_point` 命中 bbox → 得到 track_id → 检查该 track 是否仍存活。

**为什么这样就不会选错：**

- **不需要时钟同步。** `frame_id` 由机载产生、地面原样回传、机载用自己的缓冲解析——两端不需要对表，NTP/PTP 漂移问题在这里根本不存在。
- **不需要两条链路对齐。** 视频慢多少都不影响：指令引用的是"哪一帧"，不是"现在"。
- **解析结果可自证。** 机载回告它解析到了哪个 track_id，地面拿这个 ID 在**实时**画面上高亮给操作员看。操作员确认的是"现在这个框"，而不是几百毫秒前点过的位置；选错了立刻看得见。
- **失败是安全的。** 缓冲过期（链路太慢）就返回 `reference_expired`，重新选，绝不猜。

由此得到一条重要的精度分离：**显示端的时间戳配准只影响画框位置（美观），不影响指令正确性（本质）。** 显示可以粗糙（±1 帧），指令必须精确（由 `frame_id` 保证）。这两个要求被彻底拆开了。

## 6. P4 控制权（安全核心）

### 6.1 唯一发布者模型

```text
机载跟踪算法  --(控制意图: ROS topic / 本地 service)-->  gateway  --(/fmu/in/*)-->  PX4
地面 Agent    --(/providers/px4/*)------------------->  gateway
```

gateway 内部维护一个**权威租约**：

```json
{"holder": "ground" | "onboard_tracker" | "none",
 "since": 1730000000.0, "lease_expires": 1730000010.0,
 "stream_hz": 50.0}
```

- `holder=ground`：现有 `/providers/px4/*` 全部可用。
- `holder=onboard_tracker`：gateway **拒绝**地面所有会造成位移的命令，返回明确错误 `authority_held_by: onboard_tracker`；同时把跟踪器的控制意图转发为 offboard setpoint 流。
- 转移必须**显式**：`request → ack → commit`，且 UI 上有大字指示"控制权：机载"。

用 NaN 表示"该轴不控制"，与本仓库既有约定一致（见 commit `417a37a`：航点未指定航向时发 NaN，不再钉死机头）。

### 6.2 交接不能有流中断

PX4 offboard 失去 setpoint 流会在 `COM_OF_LOSS_T`（默认 0.5s 量级）后触发 failsafe。所以交接**不能**"先停后起"：

```text
1. 新持有者开始按 setpoint_hz 发布（此时 gateway 仍在转发旧源）
2. gateway 连续确认新源 N 个 tick 稳定（丢包/超时检查通过）
3. gateway 切换转发源 + 更新 holder + 立即回执地面
```

单发布者模型下这一步天然安全：gateway 全程没停过流，只是换了数据来源。

### 6.3 看门狗与接管

- **跟踪器看门狗**：持有权威期间若 N 个 tick（如 3×20ms）没有控制意图到达 → 立即撤销权威，转 hover，并通知地面。
- **地面接管永远优先**：UI 上一个物理的"接管/中止"按钮，不经 LLM、不排队、直接抢占权威 → hover 或 RTL。这是人最后的保险。
- **地面侧双保险**：`src/autonomy/safety_arbiter.py` 的 `WorldState` 增加 `authority_holder` 字段，地面 Agent 在 `holder != ground` 时连工具调用都不发；`src/agent/tool_executor.py` 的 provider 门控做第二道拦截。

### 6.4 硬限制（机载强制，不靠地面）

以下必须由机载在控制回路内强制，不能依赖地面检查：

- 距返航点最大距离（超限 → 放弃跟踪 + hover/RTL）
- 最低/最高高度
- 目标丢失策略（悬停 / 恢复搜索 / RTL），**起飞前设定**
- 最小跟随距离（防止撞目标）
- 失速/姿态异常（复用 PX4 自身）

## 7. P5 断链

| 场景 | 机载行为 | 地面行为 |
|---|---|---|
| 指挥面断，视频在 | 按事后设定继续跟踪（默认），或 hover | 只能看画面，无法中止 → 心跳要报警 |
| 指挥面断且权威在地面 | PX4 自身 offboard-loss failsafe 接管 | 重连后必须先确认权威状态再下令 |
| 全断 | 机载按 `link_loss_policy` 执行（continue / hover / RTL） | 重连后从事件流补状态 |

心跳 2Hz；`link_loss_policy` 是**起飞前**的操作员决定，机载强制。本项目不改飞控参数（沿用 `real_vehicle_deployment.md` §4.1 的原则），但机载侧的算法策略必须实现。

## 8. Agent 对话 → 准确锁定目标

这是"准确锁定"的人机回路，五步，其中第 3、4 步是成败关键：

```text
1. 语义解析
   用户: "跟着那辆白色的车"
   → {class: "car", attribute: "白色", mode: "follow"}
   前提：Agent 必须先知道机载检测器认识哪些类别（/capabilities 暴露 label set），
        否则会去要求一个模型不认识的类（"卡车"）而永远搜不到。

2. 候选获取
   读实时候选流（推送，10~30Hz）+ 一张带框标注帧。

3. 消歧（关键）
   候选 >1 时，把每个候选的【裁剪小图】喂给 VLM 打分"是否白色"，
   而不是把整帧丢给 VLM 猜。裁剪小图又便宜又准得多。
   现有 vlm_provider 已接入 inspect_current_frame（src/tools/perception_axis.py:165），
   扩展成"按候选裁剪 + 打分"即可。

4. 操作员确认（关键）
   UI 显示带编号的候选缩略图；操作员点选或说"第 2 个"。
   真机上，任何会引发自主运动的锁定都必须有人确认 —— 复用
   src/agent/approval_gate.py 的审批门与风险分级。
   理由：锁错目标 = 飞机去追一个错误的东西，这是不可回滚的物理动作。

5. 下发与监控
   lock(track_id) → 收到 locked → 申请权威转移 → 进入 follow。
   之后 Agent 持续读 track/status（距离、在框比例、目标世界坐标漂移）
   并按规则自动中止：目标丢失 > N 秒、距离 > X、电量低于阈值、检测 fps 崩塌。
```

**注意**：第 5 步之后 Agent 是**监督者**，不再逐帧参与控制。控制回路完全在机载闭合，这是与链路延迟解耦的唯一办法。

### 8.1 语义只在一处：不问机载"理解"

地面 Agent 把自然语言翻译成**一个极小的、类型化的命令集**，机载只实现这个命令集：

```text
lock(track_id, mode, params)      abort()      release_authority()
set_constraints({max_distance_m, min_alt_m, on_target_lost})
```

机载不需要理解"白色的车"、"跟着它"、"别靠太近"。**所有歧义在地面解决完，过链路的是一个无歧义、可校验的结构体。** 这样"理解"这个不可靠的东西被限制在**一个地方**（地面 Agent 的 VLM），而且它的输出还要过两道闸：

1. **活数据校验**：Agent 提出的 track_id 必须在机载当前存活的目标列表里（不存在就失败，不会瞎锁）；
2. **操作员确认**：任何引发自主运动的锁定都要人确认（第 4 步）。

机载回执必须**自证**：不是回 `ok`，而是回"我解析/执行到了什么"——`locked(track_id=17)`、`aborted(state=hovering, alt=12.3)`。地面 UI 显示的是机载的实际状态，不是命令的假设结果。

**"机载理解能否到位"这个问题因此被消解掉了**：不是靠提高机载的理解能力，而是靠把需要理解的东西从链路上移除。

### 8.2 目标选择权怎么分：推荐"机载先自主，地面异步纠正"

这决定了整条链路的耦合程度，三选一：

| 方案 | 地面作用 | 链路要求 | 风险 |
|---|---|---|---|
| A 机载全权 | 起飞前给约束，事后中止 | **最低**（几百 B/s） | 机载语义弱时选不对；人的判断用不上 |
| B 地面全权 | 机载只出候选，选择权全在地面 | 中（候选流 + 视频） | 地面来不及看/点，机载就干等 |
| **C 混合（推荐）** | **机载先自己选并开始跟，地面可否决、改选** | 中 | 需要机载支持 `lock` 与改选 |

推荐 C，因为它**把协调从关键路径上拿掉**：

- 机载不需要等地面看懂画面就能开始工作 → 不存在"地面对着延迟画面慢慢看、机载干等"的耦合；
- 地面的介入是**对一个已经在运行的过程做编辑**（改选 / 中止），而不是**启动它的前提**；
- 断链时自动退化为 A（机载继续自主），操作员恢复链路后再决定是否纠正。

由此得到总原则：**地面是异步监督者，不是同步指挥者。** 地面所有指令要么是"事前约束"，要么是"事后纠正"，永远不在机载的控制回路里等待。

## 9. 算法进程生命周期（"控制机载跑算法"）

### 9.1 具名档位，不下发命令

机载维护 `algorithms.yaml`（**白名单**）：

```yaml
profiles:
  - id: tracker_v2
    desc: "YOLO 检测 + ByteTrack 跟踪 + 视觉伺服跟随"
    launch: "ros2 launch my_pkg tracker.launch.py"
    params_schema: {target_class: str, follow_distance_m: float}
    publishes: ["/perception/targets", "/perception/annotated"]
    consumes:  ["/airsim_agent/cmd/tracker_setpoint"]
    expected_fps: {detect: 15, control: 50}
    autostart: false
```

地面 LLM 只能选择 **profile id**，永远不能下发 shell 命令。白名单在机载强制。

### 9.2 接口

```http
GET  /algorithms                → [{id, state, uptime_s, fps, cpu, gpu, mem_mb, last_error}]
POST /algorithms/{id}/start     {params}  → {ok, task_id}
POST /algorithms/{id}/stop      {mode: "graceful"|"kill"}  
GET  /algorithms/{id}/status    → 含 log_tail（最近 50 行）
POST /site/prepare              → 一键外场就绪：起 gateway + 算法 + 视频，
                                  等所有子系统健康后返回 ready（或超时并指出谁没起）
```

`/site/prepare` 是对你"到外场要手动进去启动 ROS 算法"的直接替代：地面点一下，机载把整条链路拉起来并汇报。

进程监管建议交给 **systemd（一个 profile 一个 unit）**，supervisor 只做 `start/stop/status` 包装。理由：断链后进程不会残留，崩溃能自愈，日志有 `journalctl` 兜底。

**绝不允许**：LLM 在飞行中重启算法、任意 kill 进程、改 ROS 参数。要改必须走审批门 + 机载确认。

## 10. 落地阶段（每阶段都能单独外场验证）

| 阶段 | 交付 | 外场验收标准 |
|---|---|---|
| **P0** 观测 | 机载 RTSP 拉流进地面 UI（现有 `RtspFrameSource` 即可） | 地面能看到机载画面 |
| **P1** 感知接入 | 机载 adapter 推检测流（WS）；地面 remote 引擎改推送；框叠加到画面上；补 remote 的 `annotated_frame` | 对话问"画面里有什么"答得对；框和画面对得上 |
| **P2** 目标锁定 | 候选流 + 缩略图 + 操作员确认 + `lock` 下发；机载 tracker **影子模式**（只跟踪不动飞机）+ status 回读 | 锁定 ID 在 30s 内不跳变 |
| **P3** 控制闭环 | gateway 权威租约 + 机载 setpoint 源 + 接管/中止 + 硬限制 + 断链策略 | 一键中止能在 X 秒内让飞机悬停；跟踪中地面发移动命令被**明确拒绝** |
| **P4** 生命周期 | 具名 profile + `/site/prepare` + 日志回传 + systemd 看门狗 | 地面一键拉起整条链路，无人工登录机载 |

**不要跳阶段**：P2 的影子模式（只跟踪不飞）是关键安全步骤，它让你在飞机不动的情况下验证 ID 稳定性和目标选择正确率。

## 12. 待确认（决定契约细节）

1. **相机归属**：机载检测用的相机和地面看到的图传画面是不是同一路？不是的话只能走烧框流。
2. **track_id**：机载跟踪器是否输出稳定 ID？不带 ID 的话锁定交接要复杂一个量级。
3. **锁定接口**：机载算法是否接受"锁定指定目标"的指令？还是它只做"自己检测到什么就跟什么"？后者意味着"准确锁定"这个需求在机载侧就无法满足，必须先在机载加一层目标选择器。
4. **控制输出**：机载算法现在输出什么？（`Twist` / 位置点 / 直接发 setpoint？）直接发 setpoint 的话，P4 的第一步就是把它改成发"控制意图"。
5. **链路**：指挥面走 WiFi 还是数传？数传带宽几 KB/s 只能扛指挥面，视频必须独立走图传。
6. **机载硬件**：Jetson 型号？（决定能不能同时跑检测 + 编码 + ROS）
