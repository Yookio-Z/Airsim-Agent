# 创新点 05：面向长任务循环的上下文管理（能力不裁 / 历史摘要 / 按任务收窄）

- **状态**：已实现 + 测试（`src/agent/llm.py` 的 `_compact_*` / `_relevant_tool_cards` /
  `_context_pressure`；`src/agent/events.py`；测试 `tests/test_loop_context_budget.py`）
- **一句话**：把"每轮给模型什么"定成规则——**能力声明只发一次、历史压成摘要、记忆按需取、
  菜单按任务收窄、用量驱动收紧**；核心纪律是**能力与当前观察永不裁剪**。

## 问题

- 实测每轮 ~14.8k tokens：工具卡片 5.8k + 记忆 5.6k；一张照片（base64 1.2MB ≈ 30 万 tokens）会
  把预算吃光，导致工具卡片 / 技能指导 / 记忆全被标记 `[omitted]`——恰好是模型要选动作的那一轮。
- 长任务里历史线性膨胀；旧记忆还会推荐已删除的工具（实测：`preferred_tools` 首位是已移除的检测工具）。
- 上下文过长同时抬高"内容过滤 / 首 token 截断"的概率（我们遇到过一次空回复把任务打死）。

## 我们的做法（借 Pi Agent Harness，见 `../projects/pi-agent-harness.md`）

| 规则 | 实现 | 实测 |
|---|---|---|
| 能力声明只发一次 | 原生工具调用模式不发卡片正文（schema 由 API `tools` 参数下发）；JSON 模式发精简卡片 | 卡片 13.1k→6.1k 字符；原生模式整节省略（≈3.3k tokens/轮） |
| 历史压成摘要 | `steps_digest`：一行一步（工具 / 成败 / 参数 / 关键数值），上限 24 行，最老先丢 | 20 步 5.7k→2.7k 字符，且不再随步数线性增长 |
| 记忆按需取 | 逐轮只给 session + 最近 3 条任务摘要 + guidance（工具 3/3、技能 2、风险 2）；档案交给 `memory_recall` | 记忆 23.8k→2.1k 字符（-91%） |
| 菜单按任务收窄 | 有技能激活时：常备集 ∪ 本轮用过的 ∪ 技能 `subtools`；**决策白名单仍按全量**（藏卡片 ≠ 禁用工具） | 减少无关卡片 |
| 用量驱动收紧 | 上一轮 provider 报的 `prompt_tokens` 超窗口 70% → 收紧档（摘要 8 行、只留最近 1 条结果）+ 可见事件 | 长会话不再靠"截断"保命 |
| 图片永不进上下文 | `image_base64` 一律换成 `has_image` / 字节数占位 | 防单轮 30 万 tokens 爆炸 |

## 不照搬 Pi 的部分

- **不用 LLM 写压缩摘要**：我们一步 15–40 s，摘要本身还可能被内容过滤 / 服务端抖动；
  改用零成本、可测试的确定性摘要。
- **不做可恢复会话 / 不复跑动作**：飞行指令非幂等（重放起飞 / 降落是事故），
  只做记录层恢复（残留 running 标为 interrupted）。

## 实验设计

- 指标：每轮 token 数、上下文超窗事件数、"因上下文导致的空回复 / 截断"次数、
  同任务的成功率与总耗时。
- 对照：不裁剪（原始实现） vs 现行规则；并测不同 `max_steps` 下的曲线。

## 可写成论文的句子

> 我们给出一套面向物理执行 agent 的上下文规则：把不可再生的（系统提示、当前观察、能力声明）
> 与可再生的（历史、记忆、指导文本）分开处理——前者永不裁剪，后者压缩为确定性摘要或按需取回；
> 在 UAV 长任务循环上把每轮上下文从 ~14.8k 降到 ~5–6k tokens，且不损失任务成功率。
